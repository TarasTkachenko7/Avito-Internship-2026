# AvitoNotesTasks — работа над проектом

## Цель и архитектурный статус
Довести приложение до профессионального качества, соразмерного его назначению и ТЗ из docs/assignment.md. Текущие архитектура, пакеты, паттерны и библиотеки — предмет оценки, а не обязательный стандарт.
Сохраняй качественные решения. Рефакторинг, упрощение или переработку обосновывай конкретной проблемой, альтернативами, стоимостью и проверкой. Существенные изменения архитектуры сначала предлагай пользователю. Не добавляй сложности ради Enterprise-стиля.

## Контекст по задаче
- Перед новой задачей прочитай раздел «Текущий этап» и релевантные задачи docs/plan.md, а также применимые разделы docs/android.md.
- Перед изменением Android-кода или его аудитом прочитай docs/android.md.
- Для UI дополнительно прочитай docs/ui.md; для сценария — соответствующий раздел docs/assignment.md.
- Документы нужно явно открыть: Markdown-ссылка не гарантирует их загрузку.
- Не перечитывай весь проект и справочники API без новой причины. Проверяй текущую версию исследуемого кода.

## Выполнение
- Различай анализ и реализацию. Анализ не разрешает исправлять исходники.
- Основной агент владеет задачей: исследование, решение, реализация, интеграция, проверки и отчёт.
- Критически оценивай затронутую реализацию и предлагай обоснованные улучшения; существенные архитектурные изменения за пределами текущей задачи сначала согласуй. Подтверждённые дефекты, рекомендации и непроверенные гипотезы фиксируй раздельно.
- В одной рабочей копии одновременно редактирует один агент. Рецензенты проверяют стабильный снимок или завершённый diff.
- Для значимых изменений сети, данных, жизненного цикла и сложной логики подключай android_reviewer. Для существенных UI-изменений — ui_reviewer. Небольшие задачи выполняй самостоятельно.
- Запрет делегирования в текущем запросе имеет приоритет. Если профиль недоступен, сообщи об этом; не выдавай самопроверку за независимое ревью.
- Задание рецензенту: цель, версия/снимок, область, нужные документы, критерии приёмки. Ответ: доказательства, замечания, пределы проверки.
- Общие файлы сборки, DI, навигации, темы и схемы БД изменяет назначенный основной исполнитель. Worktree используй для независимых параллельных изменений, не автоматически.

## Git и коммиты
- Перед работой проверяй Git-состояние и сохраняй существующие пользовательские изменения.
- После выполнения задачи проводи необходимые проверки и предоставляй отчёт об изменениях.
- Создавай коммиты только после моего явного подтверждения.
- До подтверждения не выполняй `git add`, `git commit` и `git push`.
- После подтверждения включай в коммит только согласованные изменения текущей задачи, не затрагивая посторонние пользовательские правки.
- Используй принятый формат Conventional Commits.
- `git push`, `reset`, `stash` и другие потенциально опасные операции выполняй только по отдельному разрешению.
